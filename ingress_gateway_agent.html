01 // Kubernetes Ingress & NGINX

An Ingress API object exposes HTTP/HTTPS services outside the cluster. NGINX Ingress watches Ingress resources and converts them into NGINX configuration.

// An Ingress usually defines:
  • ▸ Hostnames: shop.example.com
  • ▸ Paths: /api, /orders, /
  • ▸ Backend Kubernetes Services
  • ▸ TLS certificates
// Annotation-heavy advanced features:
rewrite-target
ssl-redirect
proxy-body-size
proxy-read-timeout
limit-rps
whitelist-source
enable-cors
canary-weight

Annotation-heavy configuration becomes hard to standardize, validate, and migrate at scale.

Operational risk
Critical behavior can hide inside string annotations and snippets that are hard to validate before runtime.
Portability gap
The same Ingress spec can mean different things across controllers because annotations are implementation-specific.
Migration cost
Every repository needs discovery, interpretation, conversion, validation, and a human-friendly review summary.

02 // Gateway API

The next-generation Kubernetes networking API. Traffic behavior becomes part of typed resources — not opaque annotations.

Identifies the gateway implementation
GW
Gateway
Entry point into the cluster

Defines HTTP routing behavior

Safe cross-namespace references
NOTE
Key Shift
Gateway API enables clear ownership boundaries between platform teams (Gateway) and application teams (HTTPRoute). No more controller-specific annotation dialects.
Platform owns GatewayClass + Gateway App teams own HTTPRoute Policies encode runtime behavior Review becomes typed YAML, not hidden NGINX config

03 // Envoy Gateway & Policy Model

An implementation of Kubernetes Gateway API built on Envoy Proxy — a high-performance L7 proxy. Policies express operational behavior as typed Kubernetes resources.

Policy Resource Controls Example Features
BackendTrafficPolicy Envoy ↔ backend traffic Rate limiting, retries, timeouts, circuit breaking
SecurityPolicy Security at gateway routes CORS, JWT auth, IP filtering, authorization rules
BackendTLSPolicy TLS: gateway → backend Originate TLS upstream, cert validation
ClientTrafficPolicy Client-facing edge behavior Header handling, connection options, protocol
EnvoyPatchPolicy Low-level xDS patching Custom compression, advanced Envoy filters
Why Envoy Gateway
It gives teams a Kubernetes-native control plane for Envoy, while preserving Gateway API as the portable contract between platform and application teams.
Migration reality
Gateway API covers the common routing model; Envoy Gateway policy CRDs cover operational behavior such as timeouts, rate limits, security controls, and lower-level Envoy extensions.

04b // Feature Migration Matrix

The migration is not just YAML shape-shifting. The agent must preserve behavior by mapping NGINX annotations into Gateway API filters and Envoy Gateway policy CRDs.

Feature NGINX Ingress Envoy / Gateway API Agent Review Note
URL rewrites rewrite-target HTTPRoute URLRewrite Regex rewrites may need human review.
TLS redirect ssl-redirect HTTPRoute RequestRedirect Depends on HTTP/HTTPS listener layout.
Request size proxy-body-size BackendTrafficPolicy requestBuffer.limit Preserve exact size units where possible.
Timeouts proxy-read-timeout BackendTrafficPolicy timeout.http.requestTimeout Connect/send timeout variants are called out.
Rate limiting limit-rps, limit-connections BackendTrafficPolicy rateLimit Global/distributed limits need platform design.
IP allowlists whitelist-source-range SecurityPolicy authorization Source IP preservation must be checked.
CORS enable-cors, cors-allow-* SecurityPolicy cors Origins, methods, headers must be preserved.
Headers configuration-snippet HTTPRoute HeaderModifier / ClientTrafficPolicy Simple header add/set/remove maps best.
Compression gzip on EnvoyPatchPolicy Usually filter-level Envoy config.
Canary routing canary-weight HTTPRoute backendRefs.weight Header/cookie canaries need route matches.

07 // What Are AI Agents?

An AI agent is an LLM-driven system that reasons about a task, chooses tools, observes results, and continues until the goal is complete.

01 Read task context
↓
02 Choose the right tool
↓
03 Run the tool
↓
04 Repeat until goal reached
// Why agents fit this problem:
  • ✓ Work is structured and repeatable
  • ✓ Each repo is slightly different — needs reasoning
  • ✓ Tool-driven: controlled blast radius
  • ✓ Behavior from skill files, not hardcoded scripts
  • ✓ Supports OpenAI, Gemini, Ollama via LangChain
Guardrail
The model decides the next action, but it only acts through curated tools: clone, convert, validate, push, PR, and review edits.
